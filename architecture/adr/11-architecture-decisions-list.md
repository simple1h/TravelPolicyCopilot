# Архитектурные решения Travel Policy Copilot

**Проект:** Travel Policy Copilot  
**Целевая инициатива:** Travel AI Platform  
**Тип документа:** перечень ADR и реестр решений  

---

## 1. Назначение

Документ содержит перечень архитектурных решений Travel Policy Copilot и связывает каждое ADR с требованиями, описанием текущей реализации, последствиями выбора и условиями пересмотра.

Каждое ADR позволяет установить:

- какую задачу решает выбранный подход;
- какие альтернативы были рассмотрены при последующем анализе;
- почему текущий вариант соответствует учебному MVP;
- какие положительные и отрицательные последствия связаны с выбором.

## 2. Реестр ADR

| ---------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |

## 3. Сводные основания для принятия решения

| Основание | Влияние на решения |
|---|---|
| Работающий учебный MVP | Внешний поставщик моделей, один агент, имитации внешних систем и Docker Compose |
| Требования курса | LangGraph, полноценный RAG, инструменты, измерение качества, Langfuse |
| Безопасность записи | Детерминированная проверка правил, подтверждение человеком, идемпотентность и фиксированный набор инструментов |
| Воспроизводимость | Управляемое поведение имитаций, Docker Compose и эталонные примеры |
| Ограниченные время и инфраструктура | На этапе MVP не внедряются собственная модель, несколько агентов, корпоративные интеграции и Kubernetes |
| Объяснимость | Ссылки RAG на источники и детерминированные решения по правилам |
| Возможность замены | Шлюзы, порты, адаптеры и контракты с версиями |
| Разграничение текущего и целевого состояния | Меры для промышленной эксплуатации отмечены как ещё не реализованные в MVP |

## 4. Матрица альтернатив

| Область | Выбрано | Не выбрано для MVP | Почему отложено |
|---|---|---|---|
| Размещение модели | Внешний поставщик управляемых моделей | Собственная модель или смешанная схема | Сопровождение собственной инфраструктуры GPU и моделей несоразмерно масштабу проекта |
| Устройство агента | Один граф с состоянием | Несколько агентов | Нет независимых целей и подтверждённой выгоды |
| Проверка правил | RAG и детерминированная проверка | Проверка только средствами LLM | Результат применения формальных правил должен быть воспроизводимым |
| Интеграции | Имитации, доступные через определённые контракты | Прямое подключение корпоративных систем | Нет доступа и утверждённых контрактов; внедрение требует отдельной оценки |
| Хранилище для поиска | Qdrant | Весь корпус в запросе, поиск по словам, pgvector | Выбран полноценный RAG с отдельным индексом |
| Развёртывание | Docker Compose | Kubernetes и обеспечение высокой доступности | Не определены SLO, нагрузка и требования к платформе |

---

## 5. Общие положительные последствия

- MVP остаётся выполнимым и воспроизводимым;
- решения по обязательным правилам не зависят от свободно сформированного ответа LLM;
- запись данных сосредоточена в одном месте, требует подтверждения человеком и выполняется идемпотентно;
- для интеграций и поставщика моделей предусмотрены интерфейсы, позволяющие их заменить;
- качество RAG и поведения агента можно измерять;
- сложность промышленной эксплуатации не добавляется без требований.

---

## 6. Общие отрицательные последствия

- передача данных внешнему поставщику моделей и зависимость от него;
- дополнительная сложность отдельного хранилища Qdrant и индексации малого корпуса документов;
- сеансы и контрольные точки в памяти одного процесса теряются при перезапуске;
- имитации не доказывают совместимость с корпоративными системами;
- Docker Compose не обеспечивает высокую доступность и автоматическое масштабирование;
- часть оснований выбора восстановлена после разработки и не подтверждена историческими записями;
- для пилотной эксплуатации потребуются управление доступом (IAM), долговременное хранение состояния и аудита, порядок работы с правилами и дополнительные меры эксплуатации.
