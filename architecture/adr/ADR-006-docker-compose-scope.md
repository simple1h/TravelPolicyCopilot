# ADR-006: Docker Compose для учебного MVP вместо Kubernetes

**Статус:** Принято 
**Дата фиксации:** 22.09.2026  
**Область:** развёртывание, эксплуатация, воспроизводимость и развитие  

---

## 1. Контекст

MVP включает интерфейс, Agent API, начальную загрузку, Application PostgreSQL, Qdrant, Mock Travel API и собственный экземпляр Langfuse с PostgreSQL, Redis, ClickHouse и MinIO. Для демонстрации и оценки все службы нужно воспроизводимо запускать локально.

Для промышленной эксплуатации пока не установлены SLO, требования к доступности в нескольких зонах и автоматическому масштабированию; также не измерены параллельная нагрузка и возможности команды сопровождения. Сеансы и контрольные точки находятся в памяти Agent API, поэтому запуск нескольких экземпляров API без изменения хранения состояния некорректен.

---

## 2. Основания для принятия решения

- локальная воспроизводимая демонстрация;
- несколько разнородных служб и зависимости при запуске;
- минимальная эксплуатационная сложность;
- отсутствие требования использовать Kubernetes и промышленных SLO;
- небольшая нагрузка от одного пользователя;
- необходимость сохранять данные в томах и однократно выполнять начальную загрузку;
- возможность запуска на компьютере разработчика;
- ограниченный срок учебного MVP.

---

## 3. Рассмотренные варианты

### Вариант A — ручной запуск локальных процессов

Службы Python запускаются командами, а хранилища поднимаются отдельно.

### Вариант B — Docker Compose на одном сервере

Файл конфигурации описывает сборку и образы, зависимости, порты и тома данных.

### Вариант C — Kubernetes

Для развёртывания, хранения состояния, задач, сетевого взаимодействия, секретов и наблюдения используются ресурсы кластера Kubernetes.

### Вариант D — управляемая контейнерная платформа без самостоятельной поддержки Kubernetes

Платформа предоставляет запуск контейнеров, масштабирование и управляемые хранилища.

---

---

## 5. Решение

Использовать Docker Compose на одном сервере как основной способ развёртывания учебного MVP. Ручной запуск допустим при разработке, но воспроизводимость проекта подтверждается запуском через Compose.

---

## 6. Положительные последствия

- один файл конфигурации для всех служб демонстрационной среды;
- простой порядок сборки и запуска, локальные адреса API;
- именованные тома для хранилищ;
- однократная начальная загрузка с учётом зависимостей;
- собственный экземпляр Langfuse рядом с агентом;
- воспроизводимая демонстрация и оценка;
- работа над развёртыванием остаётся соразмерной учебному проекту.

---

## 7. Отрицательные последствия и долг

- один сервер становится общей точкой отказа; службы конкурируют за его ресурсы;
- проверки работоспособности и готовности реализованы частично;
- открытые порты и локальные учётные данные небезопасны за пределами изолированной среды;
- резервное копирование, RPO/RTO и оценка необходимой мощности не определены;
- хранение сеансов в памяти препятствует безопасному запуску нескольких экземпляров API;
- Docker Compose не обеспечивает промышленную оркестрацию.

---

## 8. Риски и контроль

| Риск                                     | Контроль для MVP                                                             | Необходимое изменение для Pilot                           |
| ---------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------- |
| Нарушение порядка запуска                | Повторная проверка готовности при начальной загрузке и описание зависимостей | Полные проверки готовности перед запуском зависимых служб |
| Отказ сервера                            | Принятое ограничение учебного проекта                                        | Управляемая среда и высокая доступность согласно SLO      |
| Утрата данных                            | Именованные тома                                                             | Проверенные резервное копирование и восстановление        |
| Доступ к открытым портам                 | Предполагается локальная изоляция                                            | Закрытая сеть и шлюз с TLS                                |
| Истощение ресурсов                       | Ограниченные входные данные и количество вызовов                             | Лимиты, показатели и нагрузочные проверки                 |
| Расхождение состояния между экземплярами | Один процесс API                                                             | Долговременные сеансы и контрольные точки с версиями      |

---

## 9. Условия пересмотра

Выбор платформы развёртывания пересматривается, если:

- требуются несколько экземпляров API и обновление без остановки службы;
- утверждены требования к доступности, SLO и допустимому уровню ошибок;
- нагрузочные испытания подтверждают необходимость автоматического масштабирования;
- принят корпоративный стандарт управляемой среды выполнения;
- платформа упрощает обязательные меры сетевой защиты, IAM и контроля правил;
- хранилища состояния перенесены в службы с назначенной ответственностью за эксплуатацию.

Само по себе количество контейнеров не требует Kubernetes.
