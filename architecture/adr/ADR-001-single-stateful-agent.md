# ADR-001: Один агент LangGraph с сохранением состояния вместо многоагентной архитектуры

**Статус:** Принято 
**Дата фиксации:** 22.09.2026  
**Область:** управление работой агента, состояние, участие человека, инструменты  

---

## 1. Контекст

Copilot решает одну связанную задачу: собирает параметры поездки, получает профиль и варианты, находит правила, выполняет формальные проверки, ранжирует варианты, запрашивает выбор и подтверждение, а затем создаёт один черновик с защитой от повторной записи.

---

## 2. Основания для принятия решения

- единый прикладной сценарий и владелец состояния;
- явные остановки для участия человека и разрешение на запись;
- воспроизводимые правила переходов;
- простота тестирования и трассировки;
- отсутствие независимых целей/команд агентов;
- ограниченные границы MVP и сроки;
- необходимость предотвращать противоречивые решения и побочные эффекты;
- возможность впоследствии выделить отдельные сервисы без перехода к многоагентной архитектуре.

---

## 3. Рассмотренные варианты

### Вариант A — один агент LangGraph с сохранением состояния

Один управляющий компонент определяет последовательность узлов и инструментов, состояние, остановки и итог работы.

### Вариант B — несколько агентов под управлением координирующего агента

Координирующий агент поручает автономным агентам получение профиля, поиск, проверку правил, составление рекомендаций и согласование.

### Вариант C — полностью детерминированный сценарий без управления через LLM

Обычный прикладной автомат состояний, в котором LLM используется только для разбора ввода и составления текста либо не используется вовсе.

---

## 4. Сравнение

| Критерий | A. Один агент | B. Несколько агентов | C. Детерминированный сценарий |
|---|---|---|---|
| Соответствие связному сценарию | Высокое | Среднее | Высокое |
| Согласованность состояния | Обеспечить проще | Сложнее из-за передачи управления и общего состояния | Обеспечить проще всего |
| Участие человека и контроль записи | Централизованы | Требуют межагентных гарантий | Централизованы |
| Тестируемость | Высокая | Ниже из-за неожиданных взаимодействий | Очень высокая |
| Учебные цели по разработке агентов | Достигаются | Достигаются, но решение избыточно | Достигаются частично |
| Наблюдаемость | Единая иерархия трасс | Сопоставление действий агентов сложнее | Проще, но охватывает меньше особенностей агента |
| Трудозатраты для MVP | Умеренные | Высокие | Низкие или умеренные |
| Будущая автономность | Ограниченная, но достаточная | Высокая | Низкая |

---

## 5. Решение

Использовать один агент LangGraph с сохранением состояния для управления прикладным сценарием. Внутри него:

- LLM разбирает запрос, помогает уточнить данные и формулирует пояснения;
- доступны только инструменты из фиксированного перечня;
- проверки правил и бюджета, а также оценка вариантов детерминированы;
- выбор и подтверждение оформлены остановками и действиями;
- запись доступна только после подтверждения;
- внешние интеграции скрыты за адаптерами.

---

## 6. Положительные последствия

- один достоверный автомат состояний;
- проще доказать отсутствие записи без подтверждения;
- меньше рисков при передаче управления, конкурентном доступе и потере контекста;
- проще оценивать производительность, правильность вызовов инструментов и полноту трасс;
- единый контекст сеанса, потока выполнения и трассы;
- достаточная сложность для учебного проекта;
- прикладные компоненты можно развивать без увеличения числа агентов.

---

## 7. Отрицательные последствия и долг

- длительный сценарий зависит от устройства одного графа;
- управляющий компонент может стать слишком крупным;
- горизонтальное масштабирование невозможно без внешнего долговременного хранилища состояния;
- специализированные агенты не выполняют задачи параллельно и автономно;
- при развитии платформы распределение ответственности между командами может потребовать пересмотра границ.

---

## 8. Риски и меры контроля

| Риск                                      | Контроль для MVP                                             | Изменения для пилотной эксплуатации                                        |
| ----------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------- |
| Зацикливание                              | Не более 12 переходов                                        | Ограничения на сеанс и оповещения                                          |
| Устаревшие или конкурирующие действия     | Частичная проверка состояния и действия                      | Версия состояния или одноразовый маркер, последовательная обработка, `409` |
| Разрастание управляющего компонента       | Узлы и компоненты разделены                                  | Ответственные за модули и проверки соответствия                            |
| Передача LLM полномочий принимать решения | Ограниченный набор инструментов и детерминированные проверки | Проверки соблюдения правил                                                 |
| Масштабирование одного процесса           | Приемлемо в рамках дипломного MVP                            | Экземпляры без собственного состояния после выноса хранилища               |

---

## 9. Условия пересмотра

Многоагентную архитектуру следует рассмотреть, если одновременно появляются:

- независимые цели и предметные области;
- разные ответственные лица, целевые показатели обслуживания и правила безопасности;
- действительно параллельные длительные задачи;
- специализированные модели и инструменты с отдельным жизненным циклом;
- измеримое улучшение качества, задержки или стоимости;
- устойчивые правила передачи управления, владения состоянием и разрешения на запись;
- результаты оценки, подтверждающие преимущество перед базовой версией с одним агентом.

Само по себе увеличение числа узлов не требует перехода к многоагентной архитектуре.
