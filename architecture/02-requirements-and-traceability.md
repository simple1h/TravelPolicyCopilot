# Требования и трассируемость Travel Policy Copilot

**Проект:** Travel Policy Copilot  
**Целевая система:** Travel AI Platform  
**Тип документа:** спецификация требований


---

## 1. Назначение документа

Документ переводит проблему, контекст и границы Travel Policy Copilot в проверяемые требования к архитектуре и MVP. Он служит основанием для последующих диаграмм C2/C3 и динамических сценариев, модели данных, контрактов API, модели угроз, представления развёртывания и ADR.

Документ фиксирует бизнес-требования, функциональные требования, требования к ИИ и нефункциональные требования;


---


## 2. Бизнес-требования

| ID    | Требование                                                                                                                       | Критерий приёмки                                                                                                |
| ----- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| BR-01 | Решение должно сокращать число ручных действий, необходимых сотруднику для подготовки корпоративной командировки.                | Основной сценарий выполняется в одном диалоговом интерфейсе без ручного обращения к отдельным справочникам MVP. |
| BR-02 | Решение должно выявлять ограничения корпоративной политики до создания заявки.                                                   | Результаты проверки правил и бюджета показаны для рассматриваемых вариантов до подтверждения.                   |
| BR-03 | Рекомендация должна быть объяснимой и содержать нормативное основание.                                                           | Пользователь видит причину рекомендации и ссылки на использованные положения политики.                          |
| BR-04 | Пользователь должен сохранять контроль над созданием заявки.                                                                     | Без явного подтверждения черновик заявки не создаётся.                                                          |
| BR-05 | MVP должен демонстрировать заменяемый вертикальный срез Travel AI Platform без зависимости от реальных корпоративных интеграций. | Корпоративные системы представлены имитационными или локальными реализациями и таблицей `Target → MVP`.         |

Бизнес-эффект, фактическое сокращение времени, экономия на поездках и ROI не считаются доказанными результатами MVP.

## 3. Функциональные требования

### 3.1. Диалог и параметры поездки

| ID    | Требование                                                                                                    | Критерий приёмки                                                                                          |
| ----- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| FR-01 | Пользователь должен иметь возможность выбрать синтетический профиль сотрудника в демонстрационном интерфейсе. | Выбранный `employee_id` используется в текущей сессии.                                                    |
| FR-02 | Пользователь должен иметь возможность описать поездку на естественном языке.                                  | UI/API принимает текстовый запрос и создаёт или продолжает сессию.                                        |
| FR-03 | Система должна преобразовать запрос в типизированные параметры поездки.                                       | Результат соответствует модели типизированной модели данных; Информирование при наличии невалидных полей. |
| FR-04 | Система должна определить отсутствующие обязательные параметры.                                               | Возвращается перечень отсутствующих полей, влияющих на поиск.                                             |
| FR-05 | При недостатке данных система должна запросить уточнение и продолжить ту же сессию после ответа.              | Сценарий приостанавливается, принимает ответ и возобновляется без создания заявки.                        |

### 3.2. Получение данных и формирование вариантов

| ID    | Требование                                                                                                               | Критерий приёмки                                                                              |
| ----- | ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| FR-06 | Система должна получить профиль выбранного сотрудника через отдельный инструмент или хранилище.                          | В ходе сценария доступны категория, бюджет и применимые ограничения сотрудника.               |
| FR-07 | Система должна запрашивать варианты поездки через отдельный HTTP-контракт Mock Travel API.                               | По полному запросу возвращается типизированный список предложений либо контролируемая ошибка. |
| FR-08 | При отсутствии вариантов система должна предложить изменить ограничения, повторить попытку или завершить сценарий.       | При пустом результате поиска система не переходит к созданию заявки.                          |
| FR-09 | Система должна получить применимые положения политики для текущего запроса и профиля.                                    | Результат содержит найденные фрагменты документов и метаданные источников.                    |
| FR-10 | Система должна детерминированно проверить формализуемые правила и бюджет.                                                | Для каждого рассматриваемого варианта формируется воспроизводимое заключение.                 |
| FR-11 | Система должна ранжировать допустимые варианты прозрачным детерминированным алгоритмом.                                  | Одинаковые входные данные дают одинаковый порядок и объяснимые составляющие оценки.           |
| FR-12 | Система должна показать ранжированный список, выделенную рекомендацию, результаты проверки правил и бюджета и источники. | Все элементы доступны пользователю до выбора варианта.                                        |

### 3.3. Выбор и изменение состояния

| ID    | Требование                                                                              | Критерий приёмки                                                                                     |
| ----- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| FR-13 | Пользователь должен выбрать один из предложенных вариантов.                             | Выбранный `option_id` сохраняется в состоянии сессии.                                                |
| FR-14 | Перед созданием черновика система должна запросить явное подтверждение.                 | В сценарии есть отдельное состояние ожидания `confirmed/rejected/change_selection`.                  |
| FR-15 | При отказе пользователя система должна завершить сценарий без операции записи.          | Черновик и `approval_request_id` отсутствуют.                                                        |
| FR-16 | После подтверждения система должна создать черновик заявки и вернуть его идентификатор. | В PostgreSQL существует одна запись со статусом `draft_created`; пользователь получает `request_id`. |
| FR-17 | Повтор одной и той же подтверждённой операции не должен создавать второй черновик.      | Повтор с тем же ключом идемпотентности возвращает исходный результат либо явно сообщает о повторе.   |

### 3.4. Демонстрация и архитектурная проверяемость

| ID    | Требование                                                                                        | Критерий приёмки                                                                  |
| ----- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| FR-19 | MVP должен предоставлять демонстрационный интерфейс.                                              | Основной сценарий доступен через Streamlit UI.                                    |
| FR-20 | Демонстратор должен иметь возможность сопоставить результат с сеансом и трассой выполнения.       | Интерфейс или ответ содержит идентификатор сеанса либо трассы.                    |
| FR-21 | Должен существовать воспроизводимый набор сценариев для сравнительной оценки и проверки качества. | Набор содержит не менее 15 заранее описанных сценариев с ожидаемыми результатами. |

## 4. Требования к подсистемам ИИ, агента и RAG

### 4.1. Оркестрация и LLM

| ID     | Требование                                                                      | Критерий приёмки                                                                                                  |
| ------ | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| AIR-01 | Сценарий работы должен быть явно задан как конечный управляемый граф состояний. | Узлы, переходы, остановки и конечные состояния отражены в LangGraph, C3 и диаграммах последовательности.          |
| AIR-02 | Сценарий должен содержать не менее двух содержательных точек ветвления.         | Как минимум ветви полноты запроса и подтверждения пользователя присутствуют в графе.                              |
| AIR-03 | Должна существовать верхняя граница числа шагов/итераций.                       | Зацикливание завершается контролируемой ошибкой.                                                                  |
| AIR-04 | Ответ LLM, влияющий на сценарий, должен проходить структурную проверку.         | Результат с неверной структурой отклоняется или обрабатывается резервным механизмом.                              |
| AIR-05 | Ошибка или недоступность LLM не должна разрешать запрещённое действие.          | При ошибке поставщика запись остаётся недоступной без полного допустимого состояния и подтверждения пользователя. |
| AIR-06 | Агенту должен быть доступен только заранее определённый перечень инструментов.  | Агент не может вызвать произвольный URL, SQL или код.                                                             |

### 4.2. RAG

| ID     | Требование                                                                                                                                             | Критерий приёмки                                                                                                                   |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| RAG-01 | Корпус правил должен храниться отдельно от запроса к модели и поддерживать повторную индексацию.                                                       | Документы проходят управляемую загрузку и индексацию.                                                                              |
| RAG-02 | Загрузка должна включать разбор и нормализацию документов, деление на смысловые фрагменты, добавление метаданных и построение векторных представлений. | Для каждого фрагмента доступны текст, идентификатор источника и ключевые метаданные.                                               |
| RAG-03 | Поиск должен включать поиск по векторам, фильтрацию по метаданным, выбор первых K результатов и повторное ранжирование.                                | Этапы и параметры отражены в C3 и схеме RAG; результат содержит ранжированные фрагменты.                                           |
| RAG-04 | Пользовательское объяснение должно содержать проверяемые ссылки на нормативные источники.                                                              | Ссылку можно сопоставить с документом и разделом найденного фрагмента.                                                             |
| RAG-05 | Найденный текст должен считаться недоверенным и не должен изменять системные правила или ограничения доступа к инструментам.                           | Инструкции из документа не могут отменить подтверждение пользователя, перечень разрешённых инструментов или решение Policy Engine. |
| RAG-06 | Качество поиска должно оцениваться на эталонных сценариях.                                                                                             | Для фиксированного набора рассчитываются доля найденных подходящих источников и/или точность извлечённого контекста.               |

### 4.3. Политики и рекомендации

| ID     | Требование                                                                                                                                                                                            | Критерий приёмки                                                                |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| AIQ-01 | Денежные лимиты, формальные запреты и необходимость согласования должны вычисляться детерминированно.                                                                                                 | LLM не может самостоятельно изменить заключение Policy Engine.                  |
| AIQ-02 | Ранжирование должно быть воспроизводимым и не выдаваться за результат обученной рекомендательной модели.                                                                                              | Формула и веса документированы; одинаковый вход даёт одинаковый результат.      |
| AIQ-03 | Объяснение не должно противоречить заключениям по правилам и бюджету и указанным источникам.                                                                                                          | Программные проверки и оценка с помощью LLM выявляют противоречащие объяснения. |
| AIQ-04 | Сравнительная оценка агента должна включать успешный сценарий, уточнение, превышение бюджета, отсутствие вариантов, отказ от подтверждения, повторную запись, внешнюю ошибку и проверки безопасности. | Для каждой категории заданы ожидаемые результаты.                               |
| AIQ-05 | Набор проверок качества должен включать программные проверки, оценку с помощью LLM и проверку правильности вызова инструментов.                                                                       | Все три типа проверок выполняются независимо и формируют сводный отчёт.         |

## 5. Нефункциональные требования

### 5.1. Безопасность

| ID         | Требование                                                                                                                   | Критерий приёмки                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| NFR-SEC-01 | В MVP должны использоваться только синтетические профили, предложения и документы.                                           | В исходных данных и корпусе отсутствуют реальные персональные и коммерческие сведения.               |
| NFR-SEC-02 | Секреты не должны храниться в репозитории.                                                                                   | Настройки передаются через переменные окружения; опубликован только безопасный образец конфигурации. |
| NFR-SEC-03 | Контракты входных и выходных данных инструментов должны быть типизированы и проверяться.                                     | Некорректные аргументы не достигают внешнего сервиса или компонента записи.                          |
| NFR-SEC-04 | Возможности чтения и записи должны быть разделены.                                                                           | Инструмент записи вызывается только после отдельного подтверждённого перехода.                       |
| NFR-SEC-05 | Ни запрос к модели, ни найденный документ не должны обходить подтверждение пользователя и детерминированные проверки правил. | Проверки безопасности не приводят к запрещённой записи или изменению заключения.                     |
| NFR-SEC-06 | Вызовы внешних систем должны быть ограничены известными адресами API и инструментами.                                        | Агент не может выполнить произвольный вызов по URL, SQL-запрос или программный код.                  |
| NFR-SEC-07 | Должны применяться ограничения размера входа, времени ожидания и числа шагов.                                                | Слишком большой или продолжительный запрос завершается контролируемо.                                |
| NFR-SEC-08 | Идентификатор демонстрационного пользователя не должен выдаваться за результат полноценной проверки личности.                | C1, модель угроз и README явно указывают на использование синтетических данных и отсутствие IAM/SSO. |

### 5.2. Надёжность, состояние и целостность

| ID         | Требование                                                                                                                                       | Критерий приёмки                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| NFR-REL-01 | Ошибки внешней LLM, модели векторных представлений, Travel API, PostgreSQL и Qdrant должны преобразовываться в контролируемые прикладные ошибки. | Пользователь получает понятный ответ; сценарий не зависает и не выполняет запись.                                       |
| NFR-REL-02 | Все внешние сетевые вызовы должны иметь ограничение времени ожидания.                                                                            | Неограниченное ожидание внешнего ответа исключено.                                                                      |
| NFR-REL-03 | Повторный вызов не должен создавать вторую запись ни на уровне приложения, ни в хранилище.                                                       | Детерминированный ключ сочетается с ограничением уникальности или эквивалентной защитой.                                |
| NFR-REL-04 | Отказ средства наблюдаемости не должен останавливать основной сценарий.                                                                          | Ошибка Langfuse не отменяет корректный прикладной результат.                                                            |
| NFR-REL-05 | В дипломном MVP допускается потеря незавершённой сессии после перезапуска, но это ограничение должно быть явно документировано.                  | Документы о развёртывании и известных недостатках указывают, что сессия и контрольные точки хранятся в памяти процесса. |

### 5.3. Производительность и пропускная способность

| ID          | Требование                                                                                                                    | Критерий приёмки                                                                              |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| NFR-PERF-01 | При сравнительной оценке должна рассчитываться задержка всего сценария по 95-му процентилю без времени ожидания пользователя. | Отчёт содержит выборку, метод расчёта и p95.                                                  |
| NFR-PERF-02 | Должны отдельно наблюдаться задержки LLM, поиска и внешних инструментов.                                                      | Трасса выполнения позволяет определить вклад основных зависимостей.                           |
| NFR-PERF-03 | Должны измеряться доли успешных и ошибочных сценариев по категориям.                                                          | Показатели рассчитываются по фиксированному набору сценариев, а не по единичной демонстрации. |


### 5.4. Наблюдаемость и качество

| ID         | Требование                                                                                                                                                                            | Критерий приёмки                                                                   |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| NFR-OBS-01 | Выполнение должно иметь единые идентификаторы сеанса, сопоставления запросов и трассы.                                                                                                | По ним можно связать интерфейс, API, узлы графа, инструменты и ошибки.             |
| NFR-OBS-02 | Необходимо прослеживать вызовы LLM, узлы и переходы LangGraph, вызовы инструментов, поиск, повторное ранжирование, подтверждение пользователя, запись и ошибки.                       | В успешной и альтернативной трассах доступны фрагменты для перечисленных операций. |
| NFR-OBS-03 | Результаты оценки качества должны быть связаны с версиями модели, запроса к ней, корпуса, индекса и конфигурации.                                                                     | Результат можно воспроизвести при той же базовой конфигурации.                     |
| NFR-OBS-04 | Отчёт о качестве должен содержать не только технические счётчики, но и долю успешных сценариев, качество поиска, соответствие ответов источникам и правильность вызовов инструментов. | Показатели имеют определение, источник и связь с пользовательским сценарием.       |

### 5.5. Развёртывание и эксплуатация

| ID         | Требование                                                                                                         | Критерий приёмки                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| NFR-OPS-01 | Дипломный MVP должен воспроизводимо запускаться локально через Docker Compose.                                     | Описаны предварительные условия, переменные окружения, порядок запуска и проверки работоспособности. |
| NFR-OPS-02 | Отдельный этап первоначальной подготовки должен выполнять миграции, загрузку исходных данных и индексацию для RAG. | Повторный запуск имеет предсказуемый результат и не требует ручной правки базы данных.               |
| NFR-OPS-03 | Прикладные данные и данные средств наблюдаемости должны храниться раздельно.                                       | Представление развёртывания показывает PostgreSQL и Qdrant приложения отдельно от хранилищ Langfuse. |

### 5.6. Сопровождаемость и эволюция

| ID         | Требование                                                                                                                                               | Критерий приёмки                                                                                                                              |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-MNT-01 | Интеграции с поставщиками, профилями, правилами, LLM и заявками должны быть скрыты за явными контрактами и адаптерами.                                   | Имитационный или локальный компонент заменяется без изменения прикладного сценария.                                                           |
| NFR-MNT-02 | Архитектурные представления C2, C3, диаграмм последовательности, модели данных, API и развёртывания должны использовать согласованные имена компонентов. | Нет противоречий в границах и дублирования ответственности.                                                                                   |
| NFR-MNT-03 | Ключевые решения и отклонённые альтернативы должны быть оформлены ADR.                                                                                   | ADR описывают размещение LLM, выбор одного агента, RAG и Policy Engine, имитационные интеграции, векторное хранилище и границы развёртывания. |

## 6. Требования к данным

| ID      | Требование                                                                                                                                                              | Критерий приёмки                                                                                                  |
